## 二、改动明细与原因

### 1. 会话上下文：写记忆 + 读记忆 + 顺序归一化

**原因**：`memoryManager.addToSession` 全仓库只有测试调用，短期记忆永远是空的，
`AgentController` 读到的 `SessionContext` 也是空列表。多轮上下文完全依赖客户端
`history`，而这个字段可以被调用方任意伪造；同时前端按时间顺序追加（最旧在前），
解析器却假设"最新在前"，第 3 轮说"于娟"会补第 1 轮的谓语。

**改动**：

- `AgentController.resolveHistory`：先读 `memoryManager.getRecentTurns(sessionId, 3)`，
  取 `userMessage` 后**反转成最新在前**；记忆为空时才回退客户端 history，
  同样只取最近 3 轮并反转；
- `AgentController.rememberTurn`：成功响应后写入一轮
  （`turnNumber = getSessionTurnCount + 1`，`userMessage = 清洗后（已脱敏）query`，
  `assistantMessage = 最终答案`）；写失败只记 WARN，不影响响应（R8）；
- `MemoryManager.getRecentTurns`：新增透出方法，直接读短期存储、**不走摘要压缩**
  （摘要会把实体替换掉，消解拿不到人名）；
- `ChatRequest.history` 注释明确契约："最旧在前，服务端反转"。
  前端现有写法（`push` 后 `slice(0, -1)`）正好符合，无需改前端。

**为什么存脱敏后的 query**：`DefaultContextAggregator` 会把历史轮次拼进 Prompt。
存原文等于在"清洗已脱敏"之外新开一条 PII 进 Prompt 的通道；消解只需要人名/部门名，
不需要手机号。答案侧保持原样（工具数据已由 `ToolResultSanitizer` 处理）。

### 2. 省略补全：从"看起来像人名"改为"确实可以补"

**原因**：原判定只有"2~6 个汉字 + 不含 24 个功能字 + 无疑问词"，于是
`绩效`、`年假`、`部门`、`你好`、`谢谢` 全被当成人名，拼出
"绩效的年假还有多少""你好的年假还有多少"。

**改动**：

- 新增 `BUSINESS_NOUNS` / `GREETING_WORDS` / `METRIC_CUES` 三张表；
- 当前查询命中业务名词或寒暄词 → 不补全；
- 上一轮谓语必须含指标线索（年假/绩效/考勤/薪资/部门…），否则不补全
  （"今天天气怎么样"不会被继承）；
- `extractPredicateFromPrevious` 只在"**可继承主语 + 的 + 谓语**"时返回谓语：
  主语必须是人称代词或 2~6 字人名，且不是业务名词、不以部门/团队等组织后缀结尾；
  没有"的"、或主语是部门 → 返回 null（宁可不错）；
- 两条旧测试的期望同步修正（原来断言的正是病句行为）。

### 3. 实体提取：正向匹配 + 最短候选

**原因**：原实现取"后缀位置往前 6 个字符"，再剥一个只有 6 个词的动词前缀：

- `查一下研发部门的绩效` → 实体 `查一下研发部门` → `该部门的编制` 变成 `查一下研发部门的编制`；
- `研发部门和市场部门` → `lastIndexOf` 命中后一个，实体变成 `部门和市场部门`。

**改动**：

- 改为 `([\u4e00-\u9fa5]{1,6})(部门|团队|组|中心|事业部|…)` 正向匹配；
- 每个命中先 `stripLeadingNoise`（迭代剥离"麻烦/请/帮我/查看/查一下/给我/的/了/和…"），
  再在所有候选中取**最短**的合法实体；
- 人名提取增加 `isPersonCandidate`：拒绝业务名词、组织名，避免"研发部门"被当人；
- 快速路径改为遍历全部高置信模式，逐个替换并累积 `pairs`，
  `该员工和该部门` 不再只解一半。

### 4. LLM 层：取消、覆盖率、实体比对

**原因**：

- 超时只是 `future.get` 放弃等待，虚拟线程里的 HTTP 请求继续跑，白烧 token；
- `validateTextIntegrity` 注释写着"简化检查：return true"，实际只校验长度，
  `那他和她的绩效对比` → `张三的绩效` 这种吞掉后半句的改写能通过；
- 实体存在性用原始字符串 `contains`，历史跨行或实体带空格时误杀。

**改动**：

- `TimeoutException` 分支 `future.cancel(true)`；
- 完整性校验改为"原文非代词汉字 2-gram 覆盖率 ≥ 0.7"：
  含代词字符的 2-gram 不计入，避免把正常的代词消失算成信息丢失；
- 实体存在性比对前统一去除空白（`normalizeForMatch`）。

### 5. 消解结果复清洗

**原因**：`resolvedQuery` 来自 LLM 或规则拼接，直接成为 `finalQuery` 进入 Planner Prompt。
它绕过了入站清洗——LLM 输出里的控制字符、超长文本、数字型 PII 都没人管，
history 被污染的极端情况下还可能被注入。

**改动**：`QueryRouter` 在消解成功时对结果再走一次 `QueryCleaner`
（脱敏、截断、控制字符清理），超长时打 WARN。

### 6. 触发面

- `这个月 / 这个季度 / 这个星期 / 这些天 / 那些年 / 那时候 / 那会儿` 加入复合词剥离表，
  不再触发无意义的 LLM 调用；
- 新增 `前者 / 后者 / 上述 / 其(?=绩效|考勤|薪资|年假|…)` 代词模式，
  `其绩效如何` 终于会进入消解；
- 清掉重复常量（`其它`、`多少`）。

## 三、行为变化

| 场景 | 改前 | 改后 |
|---|---|---|
| 客户端不传 history，连续提问 | 第 2 轮起无上下文 | 同一实例同一 session 内可消解 |
| 客户端 history 与记忆同时存在 | 用客户端（可伪造） | 用记忆，客户端仅兜底 |
| 客户端 history 顺序 | 按"最新在前"解析（实际反了） | 按"最旧在前"解释后反转 |
| 上一轮"我的年假还有多少" + 本轮"绩效" | `绩效的年假还有多少` | 不补全 |
| 上一轮"研发部门有哪些人" + 本轮"于娟" | `于娟的研发部门有哪些人` | 不补全 |
| 历史"查一下研发部门的情况" + "该部门的编制" | 实体 `查一下研发部门` | 实体 `研发部门` |
| "该员工和该部门的绩效" | 只替换第一个 | 两个都替换 |
| "这个月离职率是多少" | 触发 LLM 消解 | 不触发 |
| "其绩效如何" | 永远不消解 | 触发 LLM 消解 |
| LLM 改写吞掉"对比" | 通过 | 拒绝并降级 |
| 消解结果含超长/数字 | 原样进 Prompt | 复清洗后进 Prompt |

## 六、风险与取舍

| 风险 | 影响 | 处理 |
|---|---|---|
| 开启记忆写入后第 7 轮触发摘要压缩 | 摘要器会调用 LLM，单轮延迟上升 | 写失败已 catch；如需关闭可调大 `SUMMARY_WINDOW_SIZE` |
| 省略补全变保守 | "上一轮不是指标问句"时不再补全，体验略降 | 宁可不错；真实语料回归后可放宽 `METRIC_CUES` |
| 客户端 history 被忽略 | 无状态客户端若服务端无记忆，仍可兜底 | 记忆为空时回退，行为与之前一致 |
| 消解结果复清洗 | 可能去掉 LLM 输出的尾部问号等 | 只影响格式，不影响语义 |
| 记忆存脱敏 query | 历史里的手机号会变成 `138****5678` | 消解只需要人名/部门名；避免历史成为新的 PII 通道 |
