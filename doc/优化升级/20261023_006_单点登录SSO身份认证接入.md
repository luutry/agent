## 二、改动明细与原因

### 1. 认证契约：TokenVerifier + AuthenticatedPrincipal（R11）

**原因**：HTTP 无状态，`userId` 若来自请求体即可被任意伪造，不能作为权限判定依据（违反 R2 权限前置的可信前提）。需要一个"把令牌翻译成可信身份"的唯一入口，且真实实现可替换而调用方不动。

**改动**：

- 新增 `TokenVerifier` 接口：`AuthenticatedPrincipal verify(String token)`，校验失败抛 `AuthenticationException`；
- 新增 `AuthenticatedPrincipal`（record，仅承载 `userId`）——只表达"令牌证明了你是谁"，权限仍由 `UserDirectory` 按 `userId` 解析，职责分离；
- 新增 `AuthenticationException extends AgentException`，固定 `AUTH_FAILED`（401），与既有 `PermissionDeniedException`（403）区分"不知道你是谁"与"知道但无权"。

### 2. MockTokenVerifier：解 JWT 的 sub，不验签（R11）

**原因**：SSO 授权服务器尚未接入（当前全 Mock 阶段），但链路需要可运行的身份解析；且令牌结构要与真实 OIDC JWT 一致，后续替换零改动。

**改动**：

- `@ConditionalOnProperty(name="agent.sso.verifier", havingValue="mock", matchIfMissing=true)`，缺省即装配 Mock，**无需改 `application.yml`**（R10）；
- 按 `.` 拆分令牌 → Base64URL 解码 payload 段（补齐 `=` 填充）→ Jackson 读 `sub` 作为 `userId`；
- 令牌为空 / 非 JWT 结构 / payload 非法 Base64 / 非法 JSON / 缺 `sub` 全部抛 `AuthenticationException`；
- 异常消息与日志均不含令牌原文（R4）。
- 代码处留 `// TODO(doc/TODO/019_...)`，明确"不验签、禁止用于生产"。

### 3. SsoAuthenticationFilter：认证上移到统一入口（R2/R8）

**原因**：认证是横切关注点，放在 Controller 里会散落到每个端点、且难以在业务逻辑前拦截。

**改动**：

- `OncePerRequestFilter`，`shouldNotFilter` 只放行非 `/api/agent/**` 与健康检查 `/api/agent/health`；
- 解析 `Authorization: Bearer <token>` → `TokenVerifier.verify` → `UserDirectory.resolve(userId)` → `UserContextHolder.set`；
- `finally` 中 `UserContextHolder.clear()`，防线程复用泄露（承接既有 ThreadLocal 泄露教训）；
- 缺令牌 / 非 Bearer / 校验失败：直接写 401 + `ApiResponse.fail(AUTH_FAILED)` JSON，不进入后续链路；
- **只做认证不做授权**：令牌有效但用户未知（`role=unknown`、空范围）仍放行，数据可见性交给查询层 R2 过滤，二者不混淆。

### 4. AgentController：身份取自上下文 + 一致性校验（R2/R3）

**原因**：身份既已由过滤器基于令牌装配，Controller 不应再信任请求体 `userId`。

**改动**：

- 移除 Controller 内 `userDirectory.resolve(request.getUserId())` 与 `UserContextHolder.set/clear`（生命周期归过滤器），并移除对 `UserDirectory` 的依赖；
- 从 `UserContextHolder.get()` 取可信 `authenticatedUserId`；上下文缺失 → 401；
- **一致性校验**（保留 body `userId`）：请求体 `userId` 若非空且与令牌身份不符 → 403 `PERMISSION_DENIED`，防止"令牌是 A、body 填 B"的错配/冒用；
- 下游 Planner、会话记忆写入、日志一律改用 `authenticatedUserId`，不再用 `request.getUserId()`。

### 5. 前端 index.html：携带 Bearer 令牌

**改动**：

- 新增 `buildMockToken(userId)`：本地构造 `header.payload.signature` 结构的未验签 JWT（`sub=userId`），仅联调用；
- `fetch` 增加 `Authorization: Bearer <token>` 头；
- 非 2xx 优先展示服务端 `message`，401/403 文案可见。
- 注释标明真实环境令牌应由 IdP 登录签发（TODO-019）。

## 三、行为变化

| 场景 | 改前 | 改后 |
|---|---|---|
| 无 `Authorization` 头调用 `/chat` | 200，按 body `userId` 放行 | **401**，不进入业务链路 |
| 令牌非法/无法解析 | —（无认证） | **401** |
| 令牌 `sub=A`、body `userId=A` | 200 | 200（正常） |
| 令牌 `sub=A`、body `userId=B` | 200，以 B 身份查询（越权） | **403 身份不一致**，拒绝 |
| `/api/agent/health` | 200 | 200（放行，不校验令牌） |
| `UserContext` 来源 | Controller 用 body `userId` 解析 | 过滤器用令牌 `sub` 解析 |
| ThreadLocal 清理 | Controller `finally` | 过滤器 `finally`，覆盖全部受保护端点 |

## 六、风险与回滚

| 风险 | 影响 | 回滚方式 |
|---|---|---|
| 所有 `/api/agent/**`（除 health）强制要令牌 | 未携带令牌的旧调用方一律 401 | 前端已同步携带；其它调用方需补 `Authorization` 头 |
| body `userId` 必须与令牌一致 | 二者不符时 403 | 若需放宽为"只信令牌、忽略 body"，去掉 Controller 一致性校验分支即可（`ChatRequest.isValid` 仍要求 userId 非空） |
| MockTokenVerifier 不验签 | 生产环境可被伪造令牌冒充 | 严禁用于生产；按 TODO-019 切换 `agent.sso.verifier=oidc` 装配真实验签器 |
| 过滤器成为受保护端点单点 | 过滤器异常将阻断对话 API | 逻辑已最小化并有针对性单测；异常路径统一降级为 401，不打挂容器 |
