# 015 换行与列表结构在清洗中被抹平

| 字段 | 内容 |
|---|---|
| 状态 | 待开始 |
| 优先级 | P1 |
| 关联阶段 | 输入清洗加固（20261022_004）之后 |
| 影响模块 | `preprocessor.cleaner`、`preprocessor.router` |
| 前置依赖 | 无 |

## 背景

`DefaultQueryCleaner.normalizeWhitespace` 把所有空白（含 `\n`）压成一个空格：

```
1. 年假几天
2. 病假几天
```

清洗后变成 `1. 年假几天 2. 病假几天`，两问之间不再有任何分隔符；
`RuleBasedTaskDecomposer` 只认问号、逗号、连词，识别不了列表项，于是不拆，
整段被当成一个 RAG/TOOL 问题。

用户最自然的多问题写法（换行 + 序号）反而失效，这是拆分管道的结构性盲区。

## 目标

保留换行携带的"分隔"语义，二选一或组合：

1. 清洗阶段把换行（连续换行）映射为句号，交给 `findSentenceBoundary` 与拆分器复用；
2. `RuleBasedTaskDecomposer` 增加列表项规则：按 `^\s*\d+[.、)]` / `^[-*]\s` 切分，
   并校验每项仍有独立谓语。

方案 1 改动小但会改变清洗输出（影响截断边界测试）；方案 2 需要清洗先保留换行。

## 验收标准

- [ ] 两行序号列表被拆成 2 个 unit，且各自意图独立分类
- [ ] `查一下张三的绩效和考勤` 这类并列宾语仍不拆（防回归）
- [ ] 单行普通查询的清洗结果不变（现有 645 用例全绿）
- [ ] 换行映射后不影响 `findSentenceBoundary` 的截断位置断言

## 风险

- 序号也可能出现在正文里（"第 1 条"），规则需限定行首。
- 换行语义化会改变清洗后文本长度，需同步检查截断阈值相关的观测指标。
