# 018 指代消解缓存与熔断

| 字段 | 内容 |
|---|---|
| 状态 | 待开始 |
| 优先级 | P2 |
| 关联阶段 | 指代消解与会话上下文加固（20261022_005）之后 |
| 影响模块 | `preprocessor.resolver` |
| 前置依赖 | 无 |

## 背景

LLM 指代消解对每条"含代词"的查询都要发一次真实请求，超时 1.5s。
本次已补上 `future.cancel(true)`，超时不再让请求在后台空跑，但仍有两个缺口：

1. **没有缓存**：同一会话里"他的考勤"连续问两次，会重复调用两次 LLM，结果完全相同；
2. **没有熔断**：LLM 服务整体不可用时，只有每次请求各自等异常/超时，
   没有任何"最近失败率过高就直接走规则降级"的机制。

在 QPS 2000、触发率 10% 的估算下（`ResolvePolicy` 注释），这意味着 200/s 的
消解请求全部打到 LLM；一旦下游抖动，1.5s 的排队会直接吃掉首字延迟预算。

## 目标

1. 会话内短期缓存：key = `sessionId + 归一化后的 query`，TTL 与短期记忆一致，
   命中时跳过 LLM；
2. 轻量熔断：连续 N 次超时/异常后，在冷却窗口内直接返回 unresolved（降级），
   冷却结束后放一个探测请求；
3. 指标：命中率、超时率、熔断次数，接入现有 `AgentMetric`。

## 验收标准

- [ ] 同一 query 在 TTL 内只调用一次 LLM（单测断言调用次数）
- [ ] 连续 3 次超时后，第 4 次不再发起 LLM 调用，直接降级且返回原文
- [ ] 冷却窗口结束后恢复调用
- [ ] 缓存 key 不含原文 PII（用清洗后文本或 hash）
- [ ] 熔断与缓存均可在配置中关闭（`agent.resolve-policy`）

## 风险

- 缓存 key 若用清洗后文本，工号等敏感字段仍会进入 key（本地内存，不外传，可接受）；
- 熔断阈值需要结合真实 QPS 调整，过早熔断会让多轮体验整体退化；
- 会话级缓存要跟随 `clearSession` 一起清理，否则会拿到过期上下文。
