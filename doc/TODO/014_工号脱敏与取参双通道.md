# 014 工号脱敏与取参双通道

| 字段 | 内容 |
|---|---|
| 状态 | 待开始 |
| 优先级 | P0 |
| 关联阶段 | 输入清洗加固（20261022_004）之后 |
| 影响模块 | `preprocessor.cleaner`、`planner.react`、`planner.task`、`preprocessor.model` |
| 前置依赖 | 无（与 TODO-010 取参改造可合并做） |

## 背景

R3 要求工号脱敏后才能出域，但当前 `PiiType` 没有工号模式，
`查一下 E1001 的绩效` 里的 `E1001` 会原样进入 DashScope embedding 请求与 ReAct Prompt。

不能直接在 `QueryInputDesensitizer` 里加工号模式：取参读的就是同一份文本
（`ReActEngine.extract(task.getQuery())`），`task.getQuery()` 来自
`ProcessedQuery.getFinalQuery()`，一旦在清洗阶段把工号改成 `E***`，
`ToolParameterExtractor` 就再也拿不到 employeeId。

## 目标

拆成两条通道，同一份输入产出两份文本：

1. **取参通道**：清洗（去不可见字符、全角归一化、截断）但**不脱敏**，只给 `ToolParameterExtractor` 用，不出域；
2. **模型通道**：清洗 + 脱敏（含工号），进 embedding / Prompt / RAG。

落点建议：`ProcessedQuery` 增加 `privateQuery`（原文向）字段，
`DefaultTaskDecomposer` 把它带到 `AgentTask`，`ReActEngine` 取参改读 `privateQuery`。

## 验收标准

- [ ] `查 E1001 的绩效` 的 Prompt 与 embedding 请求中不含 `E1001`
- [ ] 同一查询仍能解析出 employeeId=E1001 并命中 `employee_profile`
- [ ] `privateQuery` 不出现在任何日志、埋点、响应中（R4）
- [ ] 历史轮次同样走双通道，不得只处理当前 query

## 风险

- 两条通道容易在后续改动中漂移，需要在 `ProcessedQuery` 上写清楚字段用途。
- `privateQuery` 一旦被误传给 LLM，等于把 R3 完全绕过，落地时必须加单测守住。
