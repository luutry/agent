# 007 流式输出

| 字段 | 内容 |
|---|---|
| 状态 | 已搁置 |
| 优先级 | P2 |
| 关联阶段 | Phase 10 之后 |
| 影响模块 | `web`、`planner`、`observability` |
| 前置依赖 | 前端交互方案、网关是否支持 SSE |

## 背景

当前 `AgentController` 为同步接口：一次性返回完整答案。
Phase 10 明确不做流式（见 `doc/ROADMAP.md`）。

## 为什么暂缓

1. 前端交互未定，先做同步版本验证正确性。
2. 流式会显著增加脱敏、埋点、异常处理的复杂度，不适合在链路未稳定时引入。
3. 网关与负载均衡是否支持长连接未确认。

## 目标（未来）

新增 `POST /api/agent/chat/stream`，返回 SSE 事件流：

```
event: stage   data: {"stage":"intent","value":"TOOL"}
event: stage   data: {"stage":"tool","name":"EmployeeSearchTool"}
event: token   data: {"text":"你管辖的"}
event: citation data: {"source":"Tool","ref":"employee:1001"}
event: done    data: {"traceId":"...","tokenCost":1234}
```

## 关键设计约束

1. **脱敏必须逐块执行**：流式下无法在最后统一过滤，每个 token 块出海前都要过 `PiiMasker`，
   且要处理跨块边界的敏感串（如手机号被切成两段）。
2. **中间状态可推送，但不可泄漏**：工具名、召回数量可以推；员工姓名、绩效等级不可以。
3. **错误处理**：流已开始后出错，只能发 `event: error`，不能改 HTTP 状态码。
4. **超时策略**：首字节超时与整体超时分开配置。
5. **埋点**：需要记录「首个 token 时间」「流是否被客户端中断」。

## 验收标准（未来）

- [ ] 首 token 时间 P95 < 1.5s
- [ ] 跨块敏感串不泄漏（构造手机号被切分的用例）
- [ ] 客户端断开后服务端能感知并释放资源
- [ ] 同步接口保持可用，不破坏已有调用方

## 风险

- **脱敏边界**：这是最容易出事的点，逐块过滤必须做跨块缓冲
- **连接数**：长连接会占用线程/连接资源，需要评估网关上限
- **成本统计**：流式下 token 计数要等流结束才能确定
