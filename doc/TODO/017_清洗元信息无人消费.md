# 017 清洗元信息无人消费

| 字段 | 内容 |
|---|---|
| 状态 | 待开始 |
| 优先级 | P2 |
| 关联阶段 | 输入清洗加固（20261022_004）之后 |
| 影响模块 | `preprocessor.cleaner`、`web` |
| 前置依赖 | 无 |

## 背景

`CleanResult` 设计了 6 个元信息字段，实际只有 3 个被真正消费：

| 字段 | 消费情况 |
|---|---|
| `cleanedText` | 全链路使用 |
| `truncated` | 本轮接入：Controller 在 `issues` 里声明截断 |
| `hardRejected` | 本轮接入：Controller 直接拒答 |
| `hardLimited` | 仅日志（QueryRouter） |
| `filteredToEmpty` / `isUsable()` | 无调用点，`QueryRouter` 用 `cleaned.isBlank()` 另判 |
| `originalHash` | 无调用点，注释写着"缓存 key 用"，但项目里没有查询缓存 |
| `originalCodePoints` | 仅日志 |

`filteredToEmpty` 与 `cleaned.isBlank()` 是两套等价判断，语义已经漂移
（前者包含"脱敏后为空"的说明，后者只判空白）。

## 目标

三选一，不要维持两套：

1. 删除 `isUsable()` / `originalHash`，`QueryRouter` 改用 `filteredToEmpty`；
2. 或者引入查询缓存，把 `originalHash` 真正用作 key（截断场景下必须用原文 hash）；
3. `originalCodePoints` 接指标系统（当前只有日志）。

## 验收标准

- [ ] 全仓库对 `isUsable` / `originalHash` 的引用要么有真实调用方，要么已删除
- [ ] `QueryRouter` 的空文本判断与 `CleanResult.filteredToEmpty` 语义一致（单测覆盖）
- [ ] 若删除字段，`CleanResult.ok()` / `degraded()` 的构造同步收敛

## 风险

- 如果后续要做缓存，`originalHash` 与截断的关系需要重新确认（截断后不同原文可能同 hash）。
- 元信息收敛属于 API 变更，会影响所有构造 `CleanResult` 的测试。
