## 1. 结论摘要

这份链路文档列出的 bug（幻觉检测误判）**不是最严重的问题**。三类更值得处理：

1. **根因判断错了** —— 修的是症状（子串匹配太严），不是病灶（两份数据表示）

## 3. P0 详细分析

### P0-1 幻觉检测在修复后对"张冠李戴"完全失效

**现象【文档】**

修复前 `hallucinationScore = 0.0` → 误杀；修复后加入「数值归一化 + 关键词重叠」，假阳性消失。

**问题：假阳性消失的同时打开了假阴性。**

**反例**

```
上下文（ToolResult）：
  技术部 turnoverRate=0.05
  产品部 turnoverRate=0.03

LLM 输出（部门张冠李戴）：
  "技术部离职率 3%，产品部离职率 5%"
```

按修复后的校验：

| 检查项 | 结果 |
|---|---|
| 数值验证 | `3% → 0.03` 在上下文存在 ✓；`5% → 0.05` 存在 ✓ |
| 关键词重叠 | `技术部`、`产品部`、`离职率` 均在上下文 ✓ |
| **判定** | **hallucinationScore = 1.0 → PASS** |

**影响**

这是 HR 报表里最致命的错误类型（数字对、归属错）。修复后的检测器对它完全免疫。管理者拿到错误归属的部门指标，会做错决策——这正是 R5「不编造」要防的。

**根因**

数值验证只证明"这个数字在上下文出现过"，不证明"这个数字属于这个部门"。文本匹配匹配的是词袋，不是事实。

**建议**

改为验证三元组，不做模糊匹配：

```java
record Fact(String entity, String metric, String value, String source) {}

// 直接由 ToolResult 构造，不经文本序列化
Set<Fact> facts = { ("技术部","turnoverRate","0.05","TOOL"),
                    ("产品部","turnoverRate","0.03","TOOL") };

// 从 answer 抽三元组，精确查集合
for (Fact f : extractFrom(answer)) {
    if (!facts.contains(f)) {
        // "技术部 3%" → Fact("技术部","turnoverRate","0.03") ∉ facts → 拒绝
    }
}
```

`关键词重叠` 这条策略应当**删除**：`各部门`、`离职率` 是 query 词不是实体，出现在答案里不构成任何证据。

### P0-2 数据权限（R2）在链路里不存在

**现象【文档】**

`用户：manager_001`，`query：本月各部门离职率是多少`。

链路中唯一涉及权限的位置：

```
[3.2.3] ToolDispatcher.dispatch()
          ├─ 权限校验        ← 校验的是 team:view
```

**功能权限 ≠ 数据权限。** 全链路未出现 `DataScope`、管辖部门、汇报关系。

**影响**

- `MockHrDataProvider` 返回全部部门 → 全部数据进入 prompt → 全部返回
- 若 `manager_001` 只是技术部经理，这是**跨部门数据泄露**
- `各部门` 正是 R2 要防的越权表达

**建议**

补齐三分支，且**不允许静默返回子集**：

| 情况 | 行为 |
|---|---|
| 只有部分部门权限 | 显式说明范围：「以下是您管辖的 3 个部门」并列出部门名 |
| 无任何部门权限 | 拒绝，不调用工具 |
| 有全部门权限 | 正常返回 |

静默截断是最坏选择——用户会以为看到的是全部数据。

**【待查】** 若 `DataScope` 已在 `TeamMetricsTool` 或 Repository 内部实现而文档未提及，本条降级为"文档缺失"，但仍需补链路说明。

### P0-3 根因不是"子串匹配太严"，是"两份真相"

**现象【文档】**

```
[3.3] synthesizeAnswer()      ← 读 ReActEngine 内部格式化的 observation 文本
[4]   ContextAggregator       ← 读 ToolResult，用另一个 formatter 再格式化一次
[5]   SelfCritiqueService     ← 拿 [4] 的文本校验 [3.3] 的输出
```

**根因**

同一份数据被两个 formatter 格式化两遍，然后互相验证。只要两边字段集、顺序、精度有任何差异（`0.0523` vs `0.05`），校验必然误判。

**Envelope 是旁路，不是架构改进。**

真正的病灶是 `ReActEngine.execute()` 的返回契约不完整（只回文本，不回结构性产物），所以下游只能靠一个可变信封去别处捞。结果是两条通道并存 = 两个真相。

Envelope 还带三个后遗症：

| 后遗症 | 说明 |
|---|---|
| 阶段间隐式耦合 | 下游读某字段，不知道谁写的、何时写的 |
| 无法静态检查 | 生产者/消费者关系不可见 |
| 无限膨胀 | 每加一个功能就往信封里塞字段 |

**建议：显式契约 + 正确顺序**

```
① 预处理    → units[] + 逐单元意图
② 规划      → Plan{channel, tool, args}
③ 执行      → ExecutionResult{toolResults, retrievalResults, steps}    ← 唯一真相
④ 事实化    → FactSet{(entity, metric, value, source)}                 ← 不解文本
⑤ 前置校验  → facts 为空？权限够吗？口径完整吗？                        ← 在合成之前
⑥ 合成      → 模板 or LLM（只允许引用 FactSet 三元组）
⑦ 后置校验  → answer 的每个三元组必须 ∈ FactSet
```

注意 ⑤ 在 ⑥ 之前。当前顺序是"先花 ~4s 做 LLM 合成，再用 1ms 的规则把它否掉"——最差的时间安排。

### P0-4 性能数字不自洽；R7 无运行时中断

**数字核对**

| 文档写 | 问题 |
|---|---|
| 预处理「~10ms（含 Embedding 首次初始化 ~3.4s）」 | 10ms 不可能包含 3.4s，自相矛盾 |
| 分项和 = 10ms + 8.5s + 1ms + 1ms ≈ **8.51s** | vs 总计 **11.9s**，差 3.39s ≈ 正是那次初始化 |
| 性能表「预处理占比 0.1%」 | 实际 3.41/11.9 = **28.6%**，偏差约 280 倍 |
| 瓶颈「LLM 调用占 70%+」 | 冷启动 3.4s 不是 LLM 调用，是本地初始化，被混入 |

一张表里三个数字互相矛盾，说明是拼的，不是测的。**这种表比没有表更危险**，会误导优化方向。

**R7 没有执行点【文档】**

> 超过铁律 R7 的 30s 上限？否，11.9s < 30s

这句话本身就说明是**事后核对，不是运行时中断**。R7 要求"超限必须中止"，链路图里没有任何 watchdog / deadline 传播。

若某个 LLM 调用 hang 住 60s，当前无机制中止。

**建议**

- 性能表按实测重做，冷启动与 LLM 调用分列
- 引入 `Deadline` 在阶段间传递，每层检查 remaining，超限抛 `BudgetExceededException` 并降级

## 4. P1 详细分析

### P1-1 意图分类发生在拆分之前，TaskDecomposer 错位

**现象【文档】**

```
[2.3] QueryUnit 构建（保守实现）→ 永远 1 个单元     "已记入 TODO-009"
[3.1] TaskDecomposer.decompose()  ← 真正的分解在这里
```

**问题**

```
整句 → 意图分类（1 次）→ 分解成 N 个 task
```

复合查询永远是单意图。`本月各部门离职率和离职制度` 会被分成 2 个 task，但意图只分类了一次且是对整句，`MIXED` 的语义丢失。

**正确顺序**

```
clean → resolve → decompose → 逐 unit 分类 → 聚合
```

`TaskDecomposer` 属于**预处理**，不属于规划层。当前放在 `PlannerService` 里是位置错误。

**附带**：`QueryRouter` 声称是"预处理管道"，但 `[2.3]` 就把职责交给下游，实际只做了 clean + resolve + 一次分类，命名与职责不符。

### P1-2 ReAct 名不副实

**现象【文档】**

```
Round 1: decide() → CALL_TOOL
         inferToolName("...部门...") → team_metrics   ← 关键词命中
Round 2: decide() → FINISH
```

**三个问题**

**1. 决策与选工具脱节**

`decide()` 决定"要不要调工具"，`inferToolName()` 用关键词决定"调哪个"。两个决策者，一个用模型一个用正则，冲突时后者赢，且无人知晓。

若 `decide()` 认为该走检索，`inferToolName` 会因 query 含"部门"而覆盖成 `team_metrics`。

应为单次输出：`{action: CALL_TOOL, tool: team_metrics, args: {...}}`。

**2. 无槽位抽取**

`本月各部门` → `period=2026-10, scope=ALL_DEPARTMENTS` 由谁抽取？链路未写。若为工具内默认值，即为猜测（R5）。"入参校验"存在，但**入参从何而来**才是关键。

**3. Round 2 纯空转**

多一次 `decide()` 只为说"我完成了"：

- 多一次 LLM 往返（按 8.5s / 2 次估算约 2~4s）
- 多一份 prompt token
- 零信息增益

**顺带一个矛盾【文档】**

文档写「含 2 次 LLM 调用（决策 + 合成）」，但 `decide()` 调了两次。若两次都是 LLM，应为 3 次；若 `decide()` 是规则，则**ReAct 循环内根本没有 LLM 推理**，叫 ReAct 是贴标签。

**建议**

单意图单工具 → 直调，不走多轮。ReAct 只在"结果不足以回答、需再查"时启用（即真正的多步场景）。

### P1-3 纯 Tool 结果不该用 LLM 合成

**现象【文档】**

```
数字 → key=value → LLM 改写自然语言 → 规则校验改写对不对
```

**问题**

这是负收益闭环：为了让数字好看，引入幻觉风险，再花一整套检测器去追这个风险。同时它正是 P0-1 和 P0-3 的成因。

**建议**

纯数据类回答用模板渲染：

```java
"本月（截至 10-22）各部门离职率：技术部 5.0%（150 人）、产品部 3.0%（80 人）、销售部 8.0%（60 人）"
```

特点：确定性、零延迟、零幻觉、可精确校验。

LLM 合成只在需要**解释、归因、对比、建议**时才有价值——那时它输出推理而非数据搬运。

按文档耗时，此改动可省掉 8.5s 中约一半。

### P1-4 Jaccard 去重会误删数值型 segment【推断】

**现象【文档】**

`ContextAggregator` 用 Jaccard 相似度去重，超阈值视为重复，保留分数较高者。

**反例**

```
A: department=技术部; turnoverRate=0.05; headcount=150
B: department=产品部; turnoverRate=0.03; headcount=80
```

Token 重叠：`department`、`turnoverRate`、`headcount`、`=`、`;` → Jaccard 容易到 0.5~0.6。阈值只要 ≤0.6，**产品部被当重复删掉**。

**建议**

数值型 segment 的"重复"只能按主键判断（`entity + metric`），不能按词袋。Jaccard 仅适用于自由文本（RAG/Memory）。

**【待查】** 文档未给阈值，需读配置确认实际风险。

---

### P1-5 固定优先级 TOOL > RAG 会裁掉制度依据

**现象【文档】**

排序：`TOOL > RAG > MEMORY`，随后按 Token 预算裁剪。

**问题**

预算不足时，会优先保留 TOOL、裁掉 RAG。结果是答案有数字、没有制度依据，且 R6 来源标注缺失——静默发生。

**建议**

排序依据应为「当前意图需要的通道」，不是数据源固定优先级。若意图为 MIXED，TOOL 与 RAG 应共享预算而非互斥。

|---|---|---|---|
| P2-1 | 三级降级不可观测 | 权重矩阵 → 种子余弦 → 关键词，但无 metric/tag 标明当前级别。违反 R8「不得吞掉可观测信号」 | 每次分类打 `classifier.level` 标签，NaN 率、降级率进监控 |

| P2-5 | 539 单测未抓到 | 单测测单元行为，本 bug 是数据流契约层面，单测天然测不到 | 补端到端契约测试：给定 query + mock tool result，断言 answer 中**每个数值与实体的对应关系正确**，而非只断言非空 |
| P2-6 | "修复后 PASS"是预测非观测 | 文档写「待手工验证：重启服务后发送…确认 verdict=PASS」，但表格已写成「本例实际（修复后）verdict = PASS」 | 不要把预测写成结论。修完没跑过就不算修完 |

## 9. 附录 A：修正后的链路

```
① 预处理（QueryRouter）
   clean（含 PII 脱敏）→ resolve → decompose → 逐 unit 意图 → 聚合
   ↓ 输出：QueryUnit[]{ text, intent, confidence, slots }

② 规划（PlannerService）
   意图 + 槽位 → Plan{ channel, tool, args }
   缺槽位 → 澄清分支；单工具 → 直调，不进 ReAct
   ↓

③ 执行（ToolDispatcher / Retriever）
   权限：功能权限 + DataScope（查询条件层，R2）
   预算：Deadline 逐层检查（R7）
   ↓ 返回 ExecutionResult{ toolResults, retrievalResults, steps }

④ 事实化
   ExecutionResult → FactSet{(entity, metric, value, source)}

⑤ 前置校验（在合成之前）
   facts 为空 → INSUFFICIENT_DATA
   权限不足 → SCOPE_DENIED + 明确告知范围
   ↓

⑥ 合成
   纯数据 → 模板渲染（确定性）
   需解释 → LLM，且只允许引用 FactSet 三元组

⑦ 后置校验
   answer 的每个 (entity, metric, value) 必须 ∈ FactSet
   失败 → DEGRADED（保留原答案 + 标注问题），不是替换成"信息不足"
```

核心变化：

| 变化 | 解决的问题 |
|---|---|
| 删除 Envelope，改为显式 `ExecutionResult` | P0-3 两份真相 |
| 合成与校验共用 `FactSet` | P0-1、P0-3 |
| `DataScope` 前置到查询条件层 | P0-2 |
| `Deadline` 逐层传播 | P0-4 |
| 分段前移到预处理 | P1-1 |
| 单工具直调 | P1-2 |
| 纯数据模板渲染 | P1-3 |

## 10. 附录 B：文档质量本身的问题

作为评审对象，这份链路文档还有三个模式值得警惕：

1. **修症状不修根因** —— 加模糊匹配让告警消失，而不是消除两份数据表示
2. **用"改检测器"解决"改架构"的问题** —— 安全校验一旦为了通过而放宽，就失去校验的意义
3. **拿预测当结论** —— "修复后 PASS" 还没跑过就写进表格

第 2 条最危险：幻觉检测每放宽一次，都是在拿 R5 换绿灯。
