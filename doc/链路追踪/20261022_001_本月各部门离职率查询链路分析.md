## 二、各阶段详细分析

### 阶段 1：请求接入与信封创建

**类**：`AgentController`
**耗时**：~1ms
**做了什么**：
1. 校验 `ChatRequest` 必填字段（query、userId、sessionId）
2. 创建 `PipelineEnvelope`，生成唯一 traceId，记录 startTimeNs
3. 信封将贯穿整个流水线，收集各阶段的原始数据产物

**为什么用信封模式**：
- 解决数据流断层问题：ReActEngine 内部消费 `ToolResult`/`RetrievalResult`/`MemoryEntry` 原始对象后，只输出格式化文本；下游 `ContextAggregator` 需要原始对象，但 Controller 无法从 `AgentResponse` 获取
- 单一载体贯穿管道，各阶段写入产物、下游读取，避免跨层传递的耦合

**未做什么**：
- 尚未实现信封的阶段耗时统计自动化（当前手动 `recordStage`）
- 尚未将信封序列化用于分布式追踪

---

### 阶段 2：预处理管道（QueryRouter）

**类**：`QueryRouter`
**耗时**：~10ms（含 Embedding 首次初始化 ~3.4s）
**Trace 记录**：`stage=query_clean, duration=9ms` + `stage=coreference_resolution, duration=1ms`

#### 2.1 查询清洗（QueryCleaner）

**做了什么**：
1. 空值/空白快速返回
2. RedOS 防护硬截断（hardLimit = warnThreshold × multiplier）
3. 移除控制字符（C0/C1/零宽/双向控制符/BOM）
4. 规范化空白（含全角空格/NBSP）
5. 合并连续重复标点
6. 移除首部标点噪声
7. PII 脱敏（在截断前执行，防止截断破坏 PII 模式）
8. 语义边界截断（SENTENCE → WORD → CODE_POINT 三级回退）

**为什么需要**：用户输入可能包含噪声、注入攻击、超长文本，必须在进入后续管道前净化。PII 脱敏在截断前执行（R3 PII 不出域）。

**本例实际**：输入 `本月各部门离职率是多少` 干净无噪声，直接通过。

#### 2.2 指代消解（CoreferenceResolver）

**做了什么**：
1. 检查对话历史中是否存在可消解的代词/引用
2. 使用规则 + LLM 双层策略解析指代关系
3. 消解失败或置信度不足时，降级返回原文（宁可不错，不可错改）

**为什么需要**：多轮对话中用户可能说「它的离职率呢」，需要消解「它」指代的部门。

**本例实际**：无对话历史，无需消解，直接返回原文。

#### 2.3 QueryUnit 构建（保守实现）

**做了什么**：将 resolved 查询包装为单个 `QueryUnit`。

**未做什么**：
- 多意图检测与任务拆分（已记入 TODO-009）
- 当前保守实现，绝大多数情况只有 1 个单元

#### 2.4 意图分类（EmbeddingIntentClassifier）

**做了什么**：
1. 调用 DashScope Embedding 模型将查询编码为 1024 维向量
2. 使用线性分类头（Wx + b → softmax）计算四类意图概率
3. 输出：`T=0.790, R=0.061, M=0.141, C=0.007`
4. 判定：`TOOL (置信度 0.790)`

**为什么用 Embedding + 线性头**：
- V2 关键词投票统计「哪类关键词出现得多」，但意图的本质是「答案依赖什么外部源」
- V3 让 Embedding 编码完整语义，线性头学习「查询语义 → 依赖源」的决策边界
- 三级降级：权重矩阵 → 种子余弦相似度 → 关键词分类器

**本例实际**：首次调用触发种子 Embedding 初始化（~3.4s），后续调用直接命中缓存。

#### 2.5 路由聚合

**做了什么**：单单元直接采用其意图 `TOOL`，设置 `confidence=0.790`。

---

### 阶段 3：规划与执行（PlannerService + ReActEngine）

**类**：`PlannerService` → `ReActEngine`
**耗时**：~8.5s（含 LLM 调用）
**Trace 记录**：`ReAct engine started` → `rounds=2, status=COMPLETED`

#### 3.1 任务分解（TaskDecomposer）

**做了什么**：将预处理后的查询转换为可执行的 `AgentTask` 列表。

**本例实际**：单意图查询，分解为 1 个任务。

**未做什么**：
- 复杂多步任务分解（如「比较技术部和产品部的离职率并分析原因」）
- 当前使用 `RuleBasedTaskDecomposer`，后续需 LLM 辅助分解

#### 3.2 ReAct 循环

**做了什么**：执行「思考 → 决策 → 行动 → 观察」循环。

**Round 1**：
1. **思考**：`DecisionMaker.decide()` → `CALL_TOOL`
2. **推断工具**：`inferToolName("本月各部门离职率是多少")` → `team_metrics`（关键词「部门」命中）
3. **行动**：`ToolDispatcher.dispatch(team_metrics)`
   - 查找工具定义 → 权限校验（`team:view`）→ 入参校验 → `ToolExecutor.execute()`
   - `TeamMetricsTool` 从 `MockHrDataProvider` 获取各部门数据
   - 返回：headcount、turnoverRate、probationPassRate、performanceDistribution 等聚合指标
4. **收集产物**：`envelope.addToolResult(result)` 将原始 ToolResult 存入信封
5. **观察**：格式化为 `key=value` 文本供 LLM 消费

**Round 2**：
1. **思考**：`DecisionMaker.decide()` → `FINISH`（已有足够数据）
2. **终止循环**

**为什么用 ReAct 模式**：
- 将推理过程显式化为 Thought → Action → Observation 循环
- 支持多轮工具调用，每轮可根据前一轮结果决定下一步
- 与铁律 R7（预算硬上限：工具 ≤ 5 轮）天然契合

**本例实际**：2 轮完成（1 次工具调用 + 1 次结束），`toolResults=1`。

#### 3.3 LLM 答案合成（synthesizeAnswer）

**做了什么**：
1. 收集所有 ReAct 步骤的 observation 文本
2. 调用 `LlmService.generateAnswer(query, observations, intentCode)`
3. LLM 将原始 `key=value` 数据改写为自然语言回答

**本例实际**：
- 输入：`query="本月各部门离职率是多少"`, `observations=["department=技术部; turnoverRate=0.05; ...", ...]`
- 输出：`"各部门离职率如下：技术部5%，产品部3%，销售部8%"`（约 32 字符）

**为什么需要 LLM 合成**：
- 原始 observation 是机器可读格式（`key=value`），不适合直接展示给用户
- LLM 负责将结构化数据改写为流畅的自然语言回答

**关键问题**：LLM 改写后，文本与原始上下文的字面差异变大，导致下游幻觉检测的子串匹配策略失效。

---

### 阶段 4：上下文聚合（ContextAggregator）

**类**：`DefaultContextAggregator`
**耗时**：<1ms

**做了什么**：
1. **转换**：将信封中的 `ToolResult` → `ContextSegment`（格式化为 `key=value; key=value` 文本）
2. **排序**：按 DataSource 优先级（TOOL > RAG > MEMORY）+ 分数降序
3. **去重**：Jaccard 相似度超过阈值的视为重复，保留分数较高的
4. **裁剪**：总 Token 不超过 `MAX_TOKEN_BUDGET`（8000 tokens），段数不超过 `CONTEXT_MAX_SEGMENTS`

**为什么需要聚合**：
- 多源数据（Tool/RAG/Memory/对话）格式各异，需统一为 `ContextSegment` 供下游消费
- Token 预算控制防止超出 LLM 上下文窗口限制（R7）

**本例实际**：
- 输入：1 个 ToolResult（team_metrics 返回的各部门指标）
- 输出：`AggregatedContext{segments=1, totalTokens=~50}`
- 格式化内容示例：`"department=技术部; turnoverRate=0.05; headcount=150; ..."`

### 阶段 5：反思校验（SelfCritiqueService）

**类**：`DefaultSelfCritiqueService`
**耗时**：<1ms
**结果**：`verdict=REJECT`（**异常点**）

#### 5.1 幻觉检测（detectHallucination）

**做了什么**：
1. 将 LLM 合成的回答拆分为句子
2. 对每个句子执行三重验证：
   - **文本子串/bigram 匹配**：检查句子是否出现在上下文文本中
   - **数值验证**：提取数值并归一化百分比（`5%` → `0.05`），与上下文比对
   - **关键词重叠**：提取中文实体词（2-4字）和英文词，检查与上下文是否共享关键词
3. 计算被支持的句子比例 → `hallucinationScore`

**本例实际（修复前）**：
- 回答：`"各部门离职率如下：技术部离职率为5%"`
- 上下文：`"department=技术部; turnoverRate=0.05; ..."`
- 子串匹配：失败（LLM 改写后文本差异大）
- 数值验证：**未实现**（修复后新增）
- 关键词重叠：**未实现**（修复后新增）
- 结果：`hallucinationScore = 0.0` → `verdict = REJECT`

**本例实际（修复后）**：
- 数值验证：`5%` → `0.05`，与上下文 `turnoverRate=0.05` 匹配 → 通过
- 关键词重叠：`各部门`、`离职率`、`技术部` 在上下文中出现 → 通过
- 结果：`hallucinationScore = 1.0` → 继续后续检查

**为什么需要幻觉检测**：
- LLM 可能编造上下文中不存在的数据（铁律 R5 不编造、R6 必带来源）
- 防止 Agent 输出虚假人事数据导致管理决策失误

#### 5.2 冲突检测（detectConflict）

**做了什么**：
1. 分别提取 TOOL 和 RAG 片段中的数值
2. 检查相同指标在不同来源中是否存在 2 倍以上的差异

**本例实际**：无 RAG 结果，跳过冲突检测。

#### 5.3 完整性检查（detectIncompleteness）

**做了什么**：
1. 检查回答是否提及查询中的关键实体
2. 超过一半实体缺失则判定不完整

**本例实际**：查询实体 `["离职率", "部门"]`，回答包含两者 → 完整。

## 三、问题根因与修复

### 问题现象

查询「本月各部门离职率是多少」，Tool 成功返回数据，但响应 `verdict=REJECT`，answer 被替换为「抱歉，当前信息不足...」。

### 根因分析

**数据流断层（已修复）**：
- ReActEngine 内部消费原始对象，只输出格式化文本
- ContextAggregator 需要原始对象，Controller 无法提供
- **修复**：引入 Pipeline Envelope 管道信封模式

**幻觉检测误判（已修复）**：
- 即使数据正确传递，Self-Critique 的幻觉检测仍会误判
- 原因：LLM 将原始数据（`turnoverRate=0.05`）改写为自然语言（`离职率为5%`）
- 幻觉检测使用子串/bigram 匹配，无法识别改写后的等价内容
- **修复**：引入三种互补策略（文本匹配 + 数值验证 + 关键词重叠）

### 修复验证

- 单元测试：539 tests, 0 failures, BUILD SUCCESS
- 待手工验证：重启服务后发送「本月各部门离职率是多少」，确认 `verdict=PASS`

## 六、关键设计决策总结

| 决策 | 选择 | 理由 |
|---|---|---|
| 数据传递模式 | Pipeline Envelope 管道信封 | 解决数据流断层，单一载体贯穿管道 |
| 意图分类方案 | Embedding + 线性头（V3） | 学习「查询语义 → 依赖源」决策边界，优于关键词投票 |
| 幻觉检测策略 | 三策略互补（文本+数值+关键词） | LLM 改写后子串匹配失效，多策略更鲁棒 |
| 任务执行模式 | ReAct 循环 | 显式化推理过程，支持多轮工具调用 |
| 答案生成方式 | LLM 合成自然语言 | 原始数据机器可读，需改写为流畅文本 |
| 降级策略 | 三层降级（权重→种子→关键词） | 铁律 R8 异常隔离，防止单点失败打挂主流程 |
