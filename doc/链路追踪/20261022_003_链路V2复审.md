## 3. 新增 P0

### N1：校验阈值 0.5 允许 1/3 句子编造

**现象【文档】**

> `supported/total = 1.0`，超过阈值 **0.5** → PASS

阈值 0.5 意味着**允许一半句子是编造的**。

**反例【推算】**

```
S1: 技术部离职率 8%。        → 命中 Fact(技术部, turnoverRate, 0.08)      ✓
S2: 人力资源部离职率 5%。    → 命中 Fact(人力资源部, turnoverRate, 0.05)  ✓
S3: 财务部离职率 9%。        → Fact(财务部, turnoverRate, 0.09) ∉ FactSet ✗

supported/total = 2/3 = 0.667 > 0.5 → PASS
```

**一个含错误数字的答案通过了幻觉校验。**

**影响**

与上轮 P0-1 同类，只是从"模糊匹配放行"换成了"比例阈值放行"。两条真数据 + 一条假数据，恰好是幻觉最典型的形态（大部分对，夹一条编造的），而当前阈值对它免疫。

**建议**

| 句子类型 | 判定 |
|---|---|
| 含数值 / 实体 | **必须 100% 命中，任一未命中 → hard fail** |
| 不含数值的元话语（"以下是……"） | 可排除，用显式白名单，不用比例 |

不要用"整体比例"处理数值句。3 条数据的答案里错 1 条，恰好是最危险的那条。

### N2：FactSet 含三个互斥"人数"，校验失去判别力

**现象【文档】**

技术部的 FactSet 同时包含：

```
headcount      = 20   (编制)
currentStaff   = 15   (在职)
totalEmployees = 5    (明细人数)
```

三个互斥的"人数"全部合法进入 FactSet。

**反例【推算】**

| 用户问 | 回答 | 校验结果 |
|---|---|---|
| 技术部有多少人 | "技术部 15 人" | 命中 `currentStaff` → PASS |
| 技术部有多少人 | "技术部 5 人" | 命中 `totalEmployees` → PASS |
| 技术部有多少人 | "技术部 20 人" | 命中 `headcount` → PASS |

**三个互斥答案全部通过。**

**根因**

精确认证只校验 `(entity, value)`，metric 归属一旦映射错就失效。不确定性没有消失，只是从 **value 解析**转移到了 **metric 推断**——而"多少人"这句话根本不指明 metric，推断纯靠猜。

`totalEmployees` 与 `currentStaff` 语义重叠且数值矛盾（5 vs 15）。这不只是校验问题，是**数据模型问题**。

**建议**

1. `totalEmployees` 从 FactSet 中移除（它是数据质量指标，不是业务指标），或改名 `employeeRecordCount`
2. 强制口径命名区分：`quota`（编制）/ `onDuty`（在职）/ `withDetail`（有明细），禁止三者都叫"人数"
3. 数值句校验前先做 metric 消歧：若一句回答未指明 metric，判为不完整，不进入校验

### N3：ThreadLocal 跨线程透传 + commonPool

**现象【文档】**

> `ToolExecutor` 用 `CompletableFuture.supplyAsync`（ForkJoinPool 线程）执行工具，`UserContextHolder`（ThreadLocal）默认不跨线程传递；已在 `executeWithTimeout` 中显式捕获并透传

这是**能跑但危险**的写法。

#### N3.1 ForkJoinPool 线程复用 → 可能串用户

```
线程 T1（commonPool，长期存活）
  ├─ 任务 A（manager_001）：若在 T1 上 set 了 context，finally 在调用方线程执行 → T1 未清理
  └─ 任务 B（manager_tech）：读到 T1 残留的 manager_001 scope → 拿到全部 3 个部门
```

结果：**manager_tech 横向越权**，且只在并发时偶发，最难复现。

文档的 `finally: UserContextHolder.clear()` 在 Controller 线程执行，**清不掉 worker 线程的 ThreadLocal**。

#### N3.2 `supplyAsync` 无 executor → commonPool

commonPool 并行度 = CPU-1，且与 `parallelStream` 共享。一个 3s 超时的阻塞工具会占满它，拖垮 JVM 内其他并行任务。

#### 建议

| 问题 | 改法 |
|---|---|
| 身份传递 | `UserContext` 改为**显式参数**：`ToolContext{userId, scope}`，编译期强制，忘写就编译不过 |
| 线程池 | 注入专用 `ThreadPoolTaskExecutor`（有界队列 + 明确拒绝策略），禁止 commonPool |
| 若必须 ThreadLocal | worker 内 `try/finally` 双向清理，或 `TransmittableThreadLocal`，并配并发回归测试 |

**【待查】** 需确认透传是"作为参数传入"还是"在 worker 内 set"。前者风险可控，后者是真实越权隐患。

**【实测建议】** 并发测试：10 个不同 scope 的用户并发 100 次，断言无一次越权返回。

### N4：静默截断无声明（上轮 P0-2 残留）

**现象【文档】**

对照实验被当成"成功"：

> `manager_tech`（仅辖 DEPT_TECH）→ `离职率：技术部 8%`（只见管辖部门）

权限**强制**生效了 ✓，但**透明度**没做。用户问的是"各部门"，只得到一个部门，回答里没有任何说明。

用户的合理推断是「公司只有技术部」或「其他部门离职率为 0」——**两个都是错的**。

**建议**

渲染器需比较 `requestedScope` 与 `actualScope`：

```
if (requested == ALL && actual.size() < totalDeptCount)
    → 追加 "（仅显示您管辖的 1 个部门，全公司共 5 个）"
```

**契约缺口**：`DataScope` 现在只能**过滤**，不能**报告总数**。要生成那句声明，接口必须能回答"全公司共有几个部门"。当前接口形状不支持，需补方法或补 `ScopeReport{requested, granted, total}`。

## 4. 新增 P1

### N5："就近绑定"与模板格式隐式耦合

**现象【文档】**

> `verifyByFacts` 把回答中的数值**就近绑定实体**

这能修好当前链路（模板输出恰好是"实体 数值"相邻），但"就近"是位置启发式：

| 回答 | 结果 |
|---|---|
| `技术部与人力资源部离职率分别为 8% 和 5%` | 8% 字面更近"人力资源部" → 绑错 → **误拒** |
| `各部门离职率依次为 8%、5%、3%` | 无邻近实体 → 全部无法绑定 |
| `技术部 8%，是全公司最高` | "最高"是跨实体比较，FactSet 只有单点 → 无法验证 |

**校验器依赖渲染器的输出格式，而这个契约没有任何地方被强制。** 模板改一个标点，校验要么静默失效，要么全拒。

**建议：渲染时绑定 factId，不要事后解析**

```java
Record rendered = renderer.render(factSet, query);
// rendered.text        = "离职率：技术部 8%、人力资源部 5%、财务部 3%"
// rendered.usedFactIds = [f1, f3, f5]

// 校验退化成集合比较，零解析误差
assert rendered.usedFactIds ⊆ factSet.ids();
```

这不是过度设计——它一次性消掉 value 解析、metric 推断、实体绑定三个不确定性来源。当前方案把它们全留在了 `String` 里。

### N6：`period` 槽位未被使用

**现象【文档/推算】**

Query 是「**本月**各部门离职率」，返回：

```
离职率：技术部 8%、人力资源部 5%、财务部 3%
```

没有"本月"，没有截止日期，工具也没有 period 参数。`turnoverRate=0.08` 是 `MockHrDataProvider` 里的静态字段，与"本月"无关。

**影响**

1. 用户的限定条件被**静默忽略**
2. 答案不声明口径，用户会认为这是本月数据
3. 若 8% 实际是年度值（月度 8% ≈ 年化 96%，不可能），这是**答非所问且无提示**

上轮 P3-3 未修，而且**模板化后更难补**——以前 LLM 还有可能补一句"（本月）"，现在确定性模板不会。

**建议**

- 抽取 `period` 槽位并传给工具
- 工具若不支持时间维度，显式返回 `periodSupported=false`
- 渲染器据此声明：「该指标为当前快照，不支持按时间筛选」

**忽略用户的限定条件，是 R5 的隐性变体**——不编造数字，但编造了"这是本月数据"这个前提。

### N7：模板 / LLM 分流条件未定义

**现象【文档】**

> 纯数据走模板，不经 LLM

但"纯数据"如何判定、由谁判定，报告未写。

**风险**

- 若判定为"纯数据"但 query 实际需要解释（"为什么技术部最高"），用户看到生硬的数据堆
- 若判定为"需解释"走 LLM，则幻觉面重新出现，而 `verifyByFacts` 只能校验数值句，解释性句子无法校验

**建议**

明确分流规则，并把它写进链路文档：

| 信号 | 通道 |
|---|---|
| 意图 = TOOL 且 query 无因果/比较/建议词 | 模板 |
| 含"为什么 / 原因 / 哪个更好 / 建议" | LLM（且答案需逐句标注 factId 支撑） |
| 意图 = RAG | LLM（依据检索片段） |

### N8：权限靠 ThreadLocal 而非显式参数

**现象【文档】**

`TeamMetricsTool` 自己读 `UserContextHolder` 得到 scope。这是"约定优于强制"：每个工具都必须记得实现 scope 过滤，忘了就默认全量。

**建议**

把 scope 变成**接口签名的一部分**，让"忘写"变成编译错误：

```java
// 现在：工具内部自己 get，可以不实现
interface Tool { ToolResult execute(String query); }

// 改为：scope 强制传入
interface Tool { ToolResult execute(String query, DataScope scope); }
```

### N10：17 个种子向量支撑 4×1024 线性头（欠定）

**现象【文档】**

日志：`tool=6, rag=6, mixed=2, chitchat=3` = **17 条种子**。

用它推导 4×1024 的线性头，等于用 17 个约束定 4096 个参数——**严重欠定**。

佐证：对「本月各部门离职率是多少」这种指标查询，`M=0.141` 仍然非零，`T=0.790` 距 0.7 / 0.8 两个常见阈值都只有 0.01~0.09 的余量。

**【实测建议】5 分钟方差实验**

同一语义换 5 种说法，看 `T` 的方差：

```
本月各部门离职率
各部门本月离职率是多少
各个部门最近一个月的离职率
部门离职率本月数据
我们公司这月各部门的离职率情况
```

- 若 `T` 极差 > 0.1 → 该分类器不能用于生产路由（阈值附近会随机翻转）
- 若极小 → 说明 0.79 只是种子没调好，可以补种子

## 6. 时序反证：ReAct 循环内无 LLM（N-补充）

**现象【文档/推算】**

```
54.986  ReAct engine started
55.038  ReAct engine completed    rounds=2
```

**52ms 完成 2 轮**，其中工具执行 20ms。两次 `decide()` 共约 30ms。

LLM 调用不可能 15ms 完成 → `decide()` 是**规则**，`inferToolName` 也是关键词。

结合模板渲染，本链路 **LLM completion 调用次数 = 0**（仅 1 次 embedding API）。

**结论**

`ReActEngine` 对本路径的价值是"把 1 次同步工具调用包成 2 轮状态机"，Round 2 是纯状态机开销。

**建议**

1. 文档不该再用"显式化推理过程"作为 ReAct 的理由——这条路径没有推理
2. 统计**有多少请求真正用到 round ≥ 3**。若 < 5%，说明 ReAct 应只在复合/多工具意图下启用，简单查询走直调
3. 上轮问的"2 次还是 3 次 LLM 调用"——答案是 **0 次**，历史描述一直有误

## 10. 附录 B：正确的渲染—校验契约

当前方案：

```
FactSet → 模板渲染成 String → 再解析 String 反查 FactSet
                                  ↑ 全部不确定性集中在这里
```

建议方案：

```
FactSet → 模板渲染，同时产出 usedFactIds: List<FactId>
                                  ↓
        校验 = usedFactIds ⊆ factSet.ids() + 文本中数值与 fact.value 一一对应
                                  ↑ 零解析
```

配套约束：

| 约束 | 作用 |
|---|---|
| 渲染器只接受 `FactSet`，不接受裸数据 | 保证每个数值都能溯源到 factId |
| 模板中每个数值占位符必须绑定 factId | 编译期/启动期校验，缺绑定直接失败 |
| 校验器不解析自然语言 | 消除 N5 的整类误差 |
| 数值句 100% 命中，无比例阈值 | 消除 N1 |
| 同一 metric 只允许一个 Fact（同 entity 下） | 消除 N2 |

## 11. 一句话

V2.0 的方向是对的（单一真相源 + 确定性渲染 + 权限前置），但两个新 P0 揭示了同一个模式：

> **把不确定性从一层挪到了另一层** —— value 匹配的模糊，挪成了 metric 推断的模糊；一套解析的误差，挪成了另一套解析的误差。

真正的解法只有一个方向：**让事实从产生到校验全程不经过自然语言**。
