# Agent 查询预处理：要做什么、为什么这么做（通俗讲解）

> 背景：用户随口说的一句话，不能直接丢给大模型 / 检索 / 工具。中间有一层「预处理」，
> 把脏乱、口语、带代词的输入，整理成机器能精准理解的「标准工单」。
> 本文讲清楚：预处理到底做哪几件事、每件事的理由、本项目怎么实现、企业级通用做法。
>
> 关联代码：`src/main/java/com/luutry/agent/preprocessor/`
> （router / cleaner / resolver / rewriter / model 五个子包）

---

## 一、先讲一个生活中的例子：餐厅点单

顾客（用户）说话往往很随意：

> 「呃……上次那个菜，辣一点，不要葱，哦对了，再来份一样的，多少钱？」

后厨（LLM / 检索 / 工具）**只认标准工单，不认口语**。所以中间要有一个「服务员」（预处理）做这些事：

| 服务员做的事 | 对应预处理步骤 |
|---|---|
| 顾客口齿不清、说错字，先听清规整 | **清洗**（去噪、归一化） |
| 手机尾号、会员卡号不能写进公开小票 | **PII 脱敏**（敏感信息不出域） |
| 「上次那个菜」「一样的」→ 翻成具体菜名 | **指代消解**（代词还原） |
| 判断这是「堂食 / 外带 / 退菜 / 问价」 | **意图分类**（决定送给哪个后厨） |
| 「辣一点、不要葱」→ 拆成结构化备注 | **槽位 / 实体抽取** |
| 一句话既要主食又要甜点 → 拆成两张单 | **任务分解**（复合查询拆分） |
| 「那道菜」在不同店叫法不同 → 补几个别名方便后厨找 | **改写 / 扩展**（只给后厨，不改小票） |

**核心思想**：预处理是「用户口语」与「机器工单」之间的**翻译层 + 分拣层 + 安检层**。
没有它，后厨要么看不懂、要么看错、要么被脏数据噎住。

## 二、本项目预处理管道总览

`QueryRouter.route()` 编排的真实管道（5 步）：

```
原始输入 rawQuery
   │
   ├─ 1. clean        清洗：去噪 / 归一化 / PII脱敏 / 截断
   │
   ├─ 2. resolve      指代消解：代词 → 具体实体（带对话历史）
   │
   ├─ 3. 复合判定      拆成 units[]（当前保守：绝大多数只有 1 个单元）
   │
   ├─ 4. 逐单元分类    对每个 unit 做意图分类（向量 + 线性头）
   │                    → TOOL / RAG / MIXED / CHITCHAT
   │
   └─ 5. 路由聚合      全同意图 → 单路由；不同 → MIXED
   │
   ▼
ProcessedQuery（带 finalQuery / intent / confidence / units）→ 交给 Planner
```

产出物 `ProcessedQuery` 里带着下游要用的全部信息：清洗后文本、消解后文本、
最终查询、意图、置信度、子单元、以及各步骤的元信息（是否截断、是否消解成功等）。

> 注意：「改写 / 扩展」曾经也在管道里，后来**被移出主管道**（原因见第五节），
> 现在只作为检索侧的增强通道。这是本项目踩坑后的重要架构决策。

## 三、逐件事详解

下面每件事都按「**做什么 → 为什么 → 本项目怎么做 → 企业级怎么做**」四段讲。

### 3.1 清洗（Clean）

**做什么**：把用户输入里的「脏东西」去掉、把格式统一。本项目的 `DefaultQueryCleaner` 依次做：

```
① 空值/空白快速返回
② HARD 拒答阈值检查（超长只标记，不在这层拒答）
③ ReDoS 防护硬截断（在所有正则之前，防止超长输入把 CPU 打爆）
④ 移除控制字符（C0/C1、零宽字符、BOM、Unicode 双向控制符）
⑤ 规范化空白（全角空格 \u3000、NBSP \u00A0 → 单个空格）
⑥ 合并连续重复标点（"？？？" → "？"）
⑦ 移除首部标点噪声
⑧ 去首尾空白
⑨ PII 脱敏（手机号/身份证/邮箱/银行卡 → 138****1234）
⑩ 语义边界截断（SENTENCE → WORD → CODE_POINT 三级回退，不切断半个词/半个 emoji）
```

**为什么**：
- **脏字符会坑下游**：零宽字符、双向控制符会让正则匹配失败、让向量模型产生奇怪 embedding，
  甚至是安全攻击（Unicode 双向攻击能让人看到的和机器读到的不一样）。
- **超长输入是安全和成本问题**：几十万字符的输入直接跑正则可能触发 **ReDoS**（正则拒绝服务），
  把 CPU 占满。所以第一步就硬截断。
- **PII 不能进 LLM**（项目铁律 R3）：手机号、身份证、薪资这类敏感信息，送大模型前必须脱敏，
  否则数据出域。而且**脱敏必须在截断之前**——先截断可能把「13812341234」切成「138123」，
  正则就匹配不到了，反而泄露。

**本项目怎么做**：所有阈值外置到 `CleanPolicy`（`@ConfigurationProperties`），可不改代码调参：

| 配置项 | 默认值 | 含义 |
|---|---|---|
| `warnThresholdChars` | 1500 | 超过则标记 `truncated=true`，下游可提示「已截断」 |
| `hardRejectThresholdChars` | 2000 | 超过则标记 `hardRejected=true`，由 Controller 决定拒答 |
| `hardLimitMultiplier` | 4 | ReDoS 硬截断上限 = 1500×4 = 6000 |
| `semanticBoundaryChars` | 50 | 截断点附近向前找句子/词边界的窗口 |

清洗结果 `CleanResult` 不只返回文本，还带一堆元信息（是否截断、边界类型、原始长度、原文 hash），
供下游做差异化决策。整个 `clean()` 用 `try-catch(Throwable)` 兜底，异常就降级返回硬截断后的输入。

**企业级怎么做**：输入长度限制、编码归一化（Unicode NFKC）、WAF / 注入过滤、
敏感词与 PII 识别、去 HTML 标签、全半角统一。这一层本质是「**输入安检 + 规范化**」。

### 3.2 指代消解（Coreference Resolution）

**做什么**：把对话里的代词、指示词还原成具体实体。

```
第1轮：用户问「张三的绩效怎么样」
第2轮：用户问「他的考勤呢」   ← 「他」= 张三
       消解后 → 「张三的考勤呢」
```

**为什么**：多轮对话里，人天然会用「他 / 该员工 / 刚才那些 / 这个」。
但检索和工具**不认识代词**——你拿「他的考勤」去查数据库，数据库不知道「他」是谁。
不消解，多轮对话就无法工作。

**本项目怎么做**：`SimpleCoreferenceResolver` 是三层架构，核心原则「**宁可不错，不可错改**」：

```
Tier 1  规则触发器：query 里到底有没有独立代词？
        （先剥离"其他/因此/其中"这类含代词字符的复合词，避免误触发）
        → 没有代词，直接返回原文，不折腾

Tier 2  高置信快速路径：只处理"该员工/该部门/刚才那些"这类明确模式
        → 从对话历史里提取匹配实体，直接替换（快、准、省 LLM 调用）

Tier 3  LLM 主力消解：处理"他/她/这个"这类模糊代词
        → 委托 LlmCoreferenceResolver，结构化 prompt + 多层校验
```

任何一层出问题都**降级返回原文**（`method=DEGRADED`），绝不因为消解失败把整条链路打挂（R8）。
消解方法用 `ResolveMethod` 枚举标记（`RULE_FAST_PATH` / `LLM_RESOLUTION` / `DEGRADED`），供可观测。

**企业级怎么做**：对话状态跟踪（DST, Dialogue State Tracking）、上下文查询改写
（Contextual Query Rewriting，把多轮压成一句自包含的 query）、slot 记忆。
思路一致：**让每一轮的 query 都能脱离上下文独立被理解**。

### 3.3 意图分类（Intent Classification）

**做什么**：判断用户这句话该走哪条处理链路。本项目分 4 类（`QueryIntent`）：

| 意图 | 含义 | 触发的下游 |
|---|---|---|
| `TOOL` | 查 HR 数据（员工、团队指标、绩效） | 调用工具 → 查数据库/API |
| `RAG` | 查制度、规章、流程 | 向量检索知识库 |
| `MIXED` | 既要数据又要制度解释 | 工具 + RAG 都走 |
| `CHITCHAT` | 问候、闲聊、无关输入 | 直接回，不查任何东西 |

**为什么**：这是预处理**最核心的价值**之一。
- **省钱省时**：闲聊不该去查数据库、不该做向量检索；制度问题不该调数据工具。
  分对意图，就能**只走必要的链路**，省 token、降延迟。
- **提准确率**：查数据和查文档是两套完全不同的召回逻辑，混在一起两边都不准。
- **控权限和风险**：数据查询要做权限过滤（R2），文档检索不需要。先分类才能挂对应的安全策略。
- **兜底体验**：识别出 CHITCHAT 就能友好回应，而不是硬去检索返回「查无结果」。

**本项目怎么做**：`EmbeddingIntentClassifier`（V3 架构）——

```
query → Embedding 向量 → 离线训练好的「线性头」（权重矩阵）→ 4 类打分 → 取最高
                          │
                          ├─ 有权重矩阵：走线性头（准）
                          ├─ 无权重但有种子：走种子余弦相似度（次之）
                          └─ 都没有：降级到 KeywordIntentClassifier 关键词匹配（兜底）
```

Embedding 调用带超时，超时或返回 null 也降级到关键词分类器。**永远有兜底，不会因为分类器挂了就没意图**。

**企业级怎么做**：小模型分类器（BERT / fastText / 微调 embedding + 分类头）、
置信度阈值 + 低置信兜底、多意图识别、必要时用 LLM 做 zero-shot 分类。
关键共识：**意图分类要用轻量、快、可控的模型，别动不动就调大模型**（成本和延迟受不了）。

### 3.4 任务分解 / 复合查询（Task Decomposition）

**做什么**：一句话里有多个诉求，拆成多个独立单元分别处理。

```
「研发部离职率是多少，另外离职制度怎么规定的」
   → unit1: 研发部离职率      → TOOL
   → unit2: 离职制度          → RAG
   → 聚合：两个意图不同 → MIXED
```

**为什么**：单次检索 / 单个工具往往满足不了复合诉求。拆开后每个单元能走最合适的链路，
最后再聚合。不拆，就会出现「用查数据的方式去答制度问题」的错配。

**本项目怎么做**：`QueryRouter` 步骤 3 产生 `units[]`，步骤 4 对**每个单元独立分类**，
步骤 5 聚合（全同→单路由，不同→MIXED）。
**当前是保守实现**：绝大多数情况只有 1 个单元，多意图检测尚未接入
（见 `TODO(doc/TODO/009_多意图检测与任务分解.md)`）。架构已就位，算法待补。

**企业级怎么做**：Query Decomposition、Plan-and-Execute、multi-hop 检索、
用 LLM 把复杂问题拆成子问题列表再逐个求解（如 ReAct / 任务图）。

---

### 3.5 改写 / 扩展（Rewrite / Expansion）—— 已被移出主管道

**做什么**：同义词扩展、术语标准化、生成多个查询变体。

```
「离职流程」 → 扩展为 「离职 流程 手续 辞职 退工」，提高检索召回
```

**为什么不进主管道**（本项目踩过的坑，非常重要）：
早期版本把扩展结果当成 `finalQuery` 一路传下去，结果**两头受损**：
- **污染意图分类**：分类器训练时见的是原句，推理时却收到「离职 流失 辞退」这种拼接串，
  **训练/推理分布不一致**，准确率（F1）下降。
- **污染 LLM prompt**：把一堆同义词塞进 prompt，既费 token 又干扰大模型理解。

**本项目怎么做**：`rewrite()` 移出主管道，`ProcessedQuery.getFinalQuery()` 的优先级改为
**`resolvedQuery`（消解后原文）> `cleanedQuery`**，不再用扩展结果。
`RuleBasedQueryRewriter` 类还留在 classpath 但**已无消费者**，待清理或改造为「只服务检索通道」。

**企业级正确做法**：查询扩展**只在检索侧做**，不改用户原句。常见手段：
- 稀疏检索（BM25）用同义词词典增强；
- 稠密检索用 HyDE（先让 LLM 生成假设答案再拿去检索）；
- 多路召回（原句 dense + 原句 sparse + 术语增强 sparse）再用 RRF 融合。

一句话：**扩展是为了「多召回文档」，不是为了「改写用户的问题」。这两件事必须分开。**

---

### 3.6 槽位 / 实体抽取（Slot / Entity Filling）—— 企业级补充

**做什么**：从 query 里抽出结构化的关键信息（时间、部门、人名、指标）。

```
「研发部上个月的离职率」
   → 部门=研发部, 时间=上个月, 指标=离职率
```

**为什么**：工具调用需要**结构化参数**，不能把整句自然语言丢给 SQL。
抽出槽位才能精确地拼查询条件、做权限过滤、做时间范围限定。

**本项目现状**：`ProcessedQuery.entities` 目前**暂为空**，typed slots 尚未实现
（属于后续阶段）。指代消解里已有轻量的实体提取（从历史里找「X 的绩效」「X 部门」），
但完整的槽位抽取待补。

**企业级怎么做**：NER（命名实体识别）、时间解析（「上个月」→ 具体日期区间）、
槽位填充 + 缺槽追问（slot filling with clarification）。

## 四、为什么「顺序」极其重要（本项目的三大教训）

预处理不是「把这些事做完就行」，**做的顺序错了，结果全错**。本项目重构时修正过三个顺序错误：

| 顺序坑 | 错误做法 | 正确做法 |
|---|---|---|
| **意图分类的输入** | 用扩展后的文本分类 | **用原句/消解句分类**（保证训练=推理分布） |
| **分解 vs 分类** | 先分类再分解，子任务意图不回写 | **先分解再逐单元分类**，最后聚合 |
| **扩展的位置** | 扩展结果当 finalQuery 一路传 | **扩展移出主管道**，只进检索通道 |
| **脱敏 vs 截断** | 先截断再脱敏（半截 PII 泄露） | **先脱敏再截断**（PII 模式完整可识别） |

这些顺序背后是同一个道理：**每一步的输入，必须是「最适合这一步」的形态**，
而不是「上一步顺手产出的形态」。

## 五、为什么每一层都要「降级兜底」

预处理是**边界层**，项目铁律 R8 要求：预处理、检索、工具、记忆四层最外层 `catch(Throwable)`，
失败就降级返回原始输入或空结果，**绝不打挂主流程**。

本项目的体现：
- 清洗异常 → 返回硬截断后的输入；
- 指代消解异常 → 返回原文（`DEGRADED`）；
- 意图分类 Embedding 超时 → 降级关键词分类器 → 再不行给 CHITCHAT。

**理由**：预处理只是「锦上添花」的优化层。它挂了，大不了用脏一点的输入继续跑，
也比直接给用户抛 500 错误强。**优化层的失败，不能升级成主流程的失败。**

## 六、企业级预处理能力清单（对照本项目）

| 能力项 | 本项目现状 | 企业级典型做法 |
|---|---|---|
| 输入清洗/归一化 | ✅ `DefaultQueryCleaner` 10 步 | 编码归一化、去噪、WAF |
| 长度限制/截断 | ✅ 语义边界三级回退 + ReDoS 防护 | 硬限制 + 分片 |
| PII 脱敏 | ✅ 截断前脱敏（R3） | 脱敏/令牌化，敏感数据不出域 |
| 注入攻击过滤 | 部分（`PromptInjectionFilter` 在 security 层） | 专门的 prompt injection 检测 |
| 指代消解 | ✅ 三层（规则+LLM+降级） | DST、上下文查询改写 |
| 意图分类 | ✅ Embedding+线性头，4 类，有兜底 | 小模型分类器、多意图、置信度阈值 |
| 任务分解 | ⚠️ 架构就位，算法保守（TODO-009） | Query Decomposition、Plan-and-Execute |
| 查询改写/扩展 | ⚠️ 移出主管道，待改造为检索通道 | HyDE、多路召回、RRF 融合 |
| 槽位/实体抽取 | ⚠️ entities 暂空（后续阶段） | NER、时间解析、slot filling |
| 语言检测/翻译 | ❌ 未做 | 多语种场景需要 |
| 纠错/拼写 | ❌ 未做（仅规范化） | 拼写纠正、ASR 纠错 |
| 全程降级兜底 | ✅ 每层 catch Throwable（R8） | 熔断、降级、可观测 |

## 七、一句话总结 + 口诀

**总结**：Agent 的查询预处理，是在「用户口语」和「机器工单」之间架一层
**翻译 + 分拣 + 安检**。它做五件事——**清洗**（去脏、脱敏、截断）、
**指代消解**（代词还原）、**任务分解**（拆复合诉求）、**意图分类**（决定走哪条链路）、
**路由聚合**（合并结果）。这么做的理由是：**让下游的 LLM / 检索 / 工具拿到干净、明确、
结构化、且已做安全检查的输入，从而更准、更省、更安全**。而「改写扩展」这种
只服务检索的动作，必须移出主管道，避免污染分类和 prompt。

**记忆口诀**：

```
预处理是服务员，口语翻成标准单：
先清洗（去脏脱敏又截断），
再消解（他她它 → 具体人），
后分解（一句多求拆成几单），
再分类（数据？文档？还是闲聊？），
最后聚合定路线。
扩展只给后厨看，别改顾客的原话单。
每层都要能兜底，优化挂了不能拖垮主线。
```

**通用规律**（不止本项目）：任何生产级 Agent / RAG 系统，预处理都是「**质量、成本、安全**」
三道关口的第一道。做得好，下游事半功倍；做得糙，再强的模型也救不回来——
**垃圾进，垃圾出（Garbage In, Garbage Out）**。
