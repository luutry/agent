## 1. 现象

复合问句不会拆分，整句只按一个意图执行一次：

```
输入：团队有多少人？离职率是多少？
实际：units=1, isComposite=false，只调用一个工具/一次 RAG
期望：units=2，两个子问题各自路由
```

`我年假剩几天，另外社保基数多少`、`年假、病假分别几天` 同样只产出 1 个 unit。

## 2. 复现步骤

1. 调用 `QueryRouter.route("团队有多少人？离职率是多少？")`
2. 观察 `ProcessedQuery.getUnits().size()` 与 `isComposite()`
3. **期望**：2 个 unit、`isComposite=true`
4. **实际**：1 个 unit、`isComposite=false`

## 3. 根因

不是单点缺陷，而是**四处断点叠加**，任何一处不修拆分都不会真正生效：

| # | 断点 | 位置 | 后果 |
|---|---|---|---|
| 1 | 管道硬编码单 unit | `QueryRouter` 步骤 3 直接 `new QueryUnit(0, resolved)` | 永远只有 1 个单元 |
| 2 | 拆分器是死代码 | `preprocessor.router.RuleBasedTaskDecomposer` 无任何注入点 | 规则从未被执行 |
| 3 | 下游拿不到子任务 | `ProcessedQuery.addSubTask` 生产代码零调用，`DefaultTaskDecomposer` 却依赖 `getSubTasks()` | 即使有子任务也永远走单任务分支 |
| 4 | 意图不随子任务走 | `PlannerService` 把顶层 intent 传给每个任务 | 拆分后所有子任务仍跑同一意图，MIXED 会变成"每个子任务都 Tool+RAG" |

另外，`DataTemplateRenderer` 一次只渲染一个指标，复合查询若继续走模板会漏答另一个指标。

## 4. 方案与取舍

### 4.1 触发条件（保守，宁可漏拆）

```
拆分 = true 当且仅当任一路径产出 ≥2 个「含独立谓语」的片段：
  (a) 问号 ≥ 2
  (b) 显式并列标记（另外 / 此外 / 再问一下 / 还想问）
  (c) 逗号、分号、强连词（并且/同时/以及）切开后两侧都有独立谓语
  (d) 弱连词（和/与/及/还有）切开后两侧都有独立谓语
  (e) "分别/各自"枚举：把共享谓语补到每个枚举项
```

「独立谓语」用线索词近似：疑问词（多少/几/怎么/是否…）+ 动作词（查/看/列出/统计…）。
**不把「情况/区别/名单」等名词当谓语**，否则 `查一下张三的绩效和考勤` 会被误拆。

被明确挡住的误判：

| 输入 | 结果 | 原因 |
|---|---|---|
| `我年假还有几天` | 不拆 | "还有"表剩余，右侧片段单独无谓语 |
| `年假以及病假的区别` | 不拆 | 共享谓语"的区别" |
| `你好，我想问下年假` | 不拆 | 寒暄片段无独立谓语 |
| `查一下张三的绩效和考勤` | 不拆 | 共享谓语"查一下"，并列宾语 |

### 4.2 为什么用规则而不是 LLM

- 无新增依赖、无额外延迟、可解释、可单测；LLM 判定会引入不确定性且需要降级链。
- TODO-009 的中期方案是「LLM few-shot + 超时降级到规则」，规则层无论如何都要保留。
- 当前只有 3 类验收场景，规则足够覆盖；先落地可验证的 80%，再评估是否值得上模型。

### 4.3 为什么同时打通 subTasks 与 per-task intent

只改 `QueryRouter` 产出 units 也能让验收用例变绿，但那正是复审 P1-1 指出的问题——
**数据产出了却没人消费**，属于装饰性拆分。因此本次一并：

- 把每个 unit 的意图回填到对应 `SubTask`；
- `DefaultTaskDecomposer` 把 `SubTask.intent` 写入 `AgentTask`；
- `PlannerService` 按 `AgentTask.intent` 执行，顶层意图只在任务未携带时兜底。

这样 `团队有多少人？离职率是多少？` 会真正产生两个任务、两次工具调用，而不是一次。

### 4.4 为什么复合查询的答案不走模板

`DataTemplateRenderer` 按「一个指标」渲染（`resolveMetric` 只返回一个 metric）。
复合查询往往包含多个指标或多个来源，继续走模板会静默漏答。因此复合查询回退 LLM 汇总，
再由 `FactSet` 做含数值句的 100% 硬校验兜底（R5 不放松）。

### 4.5 本次没做

- **slots 未随 unit 下发**：TODO-009 的前置依赖 TODO-010 尚未落地；当前仍由
  `ToolParameterExtractor` 在 ReAct 层按整句子抽参。
- **dependent 顺序执行**：`SubTask.dependent` 未赋值，子任务目前按顺序同步执行，已足够。
- **超限声明**：超过 5 个子任务时截断并 `WARN` 日志，暂未在答案里向用户声明。

## 7. 回归风险

| 风险 | 说明 | 缓解 |
|---|---|---|
| 行为变化 | `查看员工绩效，同时看看考勤情况` 从 1 unit 变为 2 unit | 已更新断言；属预期修复 |
| 复合 TOOL 答案精度 | 不再走确定性模板，改 LLM 汇总 | FactSet 数值硬校验兜底；无 LLM 时降级拼接 |
| 严格校验误拒 | 复合答案走 LLM 后，含数值句必须 100% 命中 FactSet，LLM 若补充"共 3 个部门"这类未入 FactSet 的数字会被 REJECT | 属 R5 预期代价；后续可把部门总数等聚合值纳入 FactSet |
| 误拆 | 谓语线索是启发式，可能把长句拆碎 | 四条防误拆用例；后续可用真实 query 样本回归 |
| 截断静默 | 超过 5 个子任务只保留前 5 个 | WARN 日志；答案声明待补 |
