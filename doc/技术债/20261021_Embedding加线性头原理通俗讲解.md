# Embedding + 线性头 原理通俗讲解

> 如果你不熟悉机器学习，读完本文就能理解它做了什么、为什么这样做、以及我们项目里是怎么用的。

---

## 一、先讲一个生活中的例子

### 水果分拣

想象你是一个水果仓库的质检员，需要把传送带上的水果分成四类：**苹果、橙子、香蕉、葡萄**。

**方案 A（关键词规则）**：你拿着一张清单，上面写着每种水果的特征：
- 苹果：红色、圆形、有果梗
- 橙子：橙色、圆形、表皮粗糙
- 香蕉：黄色、长条形
- 葡萄：紫色、小圆球、成串

每来一个水果，你就对照清单数："这个有红色(+1)、圆形(+1)、有果梗(+1) = 3分，最像苹果！"

**问题**：来了一个"青苹果"——它是绿色的（和橙子颜色冲突）、圆形的（和橙子一样）、有果梗（和苹果一样）。你数了半天，发现"绿色+圆形"让它更像橙子，但直觉告诉你它是苹果。规则不够用了。

**方案 B（Embedding + 线性头）**：你有一台"水果扫描仪"（Embedding 模型），把水果放进去，它吐出一张**体检报告**（向量），上面有几百个指标（甜度、酸度、水分、硬度、形状、气味……），这些指标综合描述了水果的**本质特征**。

然后你有一个"评分表"（线性头 Wx+b），上面写着四类水果各指标的权重：

```
苹果分 = 0.8×甜度 + 0.3×酸度 + 0.1×水分 + ... + 偏置
橙子分 = 0.2×甜度 + 0.7×酸度 + 0.5×水分 + ... + 偏置
香蕉分 = ...
葡萄分 = ...
```

哪个分高就是哪个。

**关键区别**：
- 方案 A 靠**人工编规则**（"红色=苹果"），容易出错
- 方案 B 靠**机器理解本质特征**（几百个维度的综合评分），更准确

## 二、回到我们的项目：意图分类

### 2.1 V2 的"关键词规则"方案

我们的 Agent 需要判断用户查询属于哪类意图：
- **TOOL**：需要查人事数据库（"查看团队人员"、"张三的绩效"）
- **RAG**：需要查制度文档库（"绩效制度是什么"、"离职流程怎么走"）
- **MIXED**：两者都需要（"查看员工绩效并对比制度"）
- **CHITCHAT**：闲聊（"你好"、"谢谢"）

V2 `KeywordIntentClassifier` 的做法就是"方案 A"：

```java
// V2 核心逻辑
int toolHits = countKeywordHits(query, ["员工", "绩效", "查看", "团队", ...]);
int ragHits  = countKeywordHits(query, ["制度", "怎么", "如何", "什么", ...]);

// 哪边命中多 → 哪边赢
if (toolHits > ragHits) return TOOL;
else if (ragHits > toolHits) return RAG;
```

### 2.2 V2 的根本缺陷

**缺陷一：共享关键词污染**

看这两个查询：

| 查询 | 真实意图 | 关键词分析 |
|------|---------|-----------|
| "绩效怎么算" | RAG（问制度规则） | "绩效"→TOOL+1, "怎么"→RAG+1 → 打平 |
| "看看张三绩效" | TOOL（要查数据） | "看看"→TOOL+1(?), "绩效"→TOOL+1 → TOOL赢 |

第一个查询，"绩效"同时出现在 TOOL 关键词列表里（因为查绩效数据也用这个词），但用户问的是**制度**不是**数据**。关键词分类器无法区分。

**缺陷二：句式轴和依赖源轴正交**

"怎么"这个词出现在 RAG 关键词列表里，但：
- "绩效**怎么**算" → 问制度 → RAG ✅
- "**怎么**查看员工绩效" → 要数据 → TOOL ✅

同一个"怎么"，两种完全不同的意图。因为**句式**（怎么/如何/看看）决定的是"问什么类型的问题"，而**意图**决定的是"答案在哪里"。这两个轴是正交的，用句式猜意图，必然出错。

### 2.3 V3 的"Embedding + 线性头"方案

```
用户查询: "绩效怎么算"
    │
    ▼
① Embedding 模型（DashScope text-embedding-v3）
   把整句话编码为 1024 维向量:
   [0.012, -0.034, 0.056, ..., 0.001]
    │
    │  这个向量不是随机的！它编码了句子的"语义本质"：
    │  - "绩效怎么算" 的向量 和 "制度规定" 的向量 距离很近
    │  - "绩效怎么算" 的向量 和 "查数据库" 的向量 距离较远
    │  - 即使它们共享"绩效"这个词
    │
    ▼
② 线性分类头（Wx + b）
   权重矩阵 W 是 4×1024（4个类别，每个类别1024维权重）:

   TOOL分   = W[0]·向量 + b[0] = 0.3
   RAG分    = W[1]·向量 + b[1] = 1.8  ← 最高！
   MIXED分  = W[2]·向量 + b[2] = 0.1
   CHITCHAT分 = W[3]·向量 + b[3] = -0.5
    │
    ▼
③ Softmax 归一化 → 概率分布
   [0.08, 0.72, 0.05, 0.15]
    │
    ▼
④ 取最大概率类别 → RAG（置信度 0.72）✅
```

## 三、Embedding 到底是什么？

### 3.1 一句话解释

**Embedding = 把文字变成一组数字，让"意思相近"的文字，数字也相近。**

### 3.2 具体例子

假设我们用 3 个维度来描述一句话（实际是 1024 维）：

| 句子 | 维度1: 问制度? | 维度2: 要数据? | 维度3: 闲聊? |
|------|-------------|-------------|------------|
| "绩效制度是什么" | 0.9 | 0.1 | 0.0 |
| "绩效怎么算" | 0.8 | 0.1 | 0.0 |
| "离职规定有哪些" | 0.7 | 0.2 | 0.0 |
| "查看员工绩效" | 0.1 | 0.9 | 0.0 |
| "团队有多少人" | 0.0 | 0.8 | 0.1 |
| "你好" | 0.0 | 0.0 | 0.9 |
| "谢谢" | 0.0 | 0.1 | 0.8 |

看到了吗？
- "绩效制度是什么" 和 "绩效怎么算" 虽然措辞不同，但向量很接近（都是问制度）
- "绩效怎么算" 和 "查看员工绩效" 虽然共享"绩效"，但向量差很远（一个问制度，一个要数据）

**这就是 Embedding 的魔力：它理解语义，不只是匹配字面。**

### 3.3 我们用的 Embedding 模型

```yaml
# application.yml
llm:
  qwen:
    embedding-model-name: "text-embedding-v3"  # DashScope 的 Embedding 模型
    base-url: "https://dashscope.aliyuncs.com/compatible-mode/v1"
```

- 输入：一段中文文本（如 "绩效怎么算"）
- 输出：1024 维浮点数向量（如 `[0.012, -0.034, 0.056, ...]`）
- 耗时：约 100ms
- 通过 langchain4j 的 OpenAI 兼容 API 调用

## 四、线性头到底是什么？

### 4.1 一句话解释

**线性头 = 一个评分表，每个类别一行，每行有 1024 个权重，对应 Embedding 的 1024 个维度。**

### 4.2 数学公式（不要被吓到，其实就是加权求和）

```
RAG分数 = W[0][0]×emb[0] + W[0][1]×emb[1] + ... + W[0][1023]×emb[1023] + bias[0]
```

翻译成中文：
```
RAG分数 = 第1个权重×第1维向量值 + 第2个权重×第2维向量值 + ... + 偏置
```

就是**加权求和**，小学算术。

### 4.3 四个类别各算一遍

```java
// 伪代码，实际在 EmbeddingIntentClassifier.classifyByLinearHead() 中
double[] logits = new double[4];  // [TOOL分, RAG分, MIXED分, CHITCHAT分]

for (int c = 0; c < 4; c++) {
    double score = bias[c];  // 偏置（基础分）
    for (int i = 0; i < 1024; i++) {
        score += weights[c][i] * embedding[i];  // 加权求和
    }
    logits[c] = score;
}

// logits 可能是 [0.3, 1.8, 0.1, -0.5]
// 然后 softmax 归一化为概率 [0.08, 0.72, 0.05, 0.15]
```

### 4.4 权重从哪来？

**冷启动（当前阶段）**：权重为空，不启用线性头，改用"种子余弦相似度"（后面讲）。

**训练完成后**：
1. 收集一批标注数据：`(查询文本, 正确意图标签)`
2. 用 Embedding 模型把查询文本转为向量
3. 用机器学习算法（逻辑回归/线性 SVM）训练出权重矩阵 W 和偏置 b
4. 把 W 和 b 填入 `application.yml`，热更新生效

```yaml
agent:
  intent-classification:
    weights:
      - [0.012, -0.003, ...]  # TOOL 的 1024 维权重
      - [-0.008, 0.015, ...]  # RAG 的 1024 维权重
      - [0.005, 0.002, ...]   # MIXED 的 1024 维权重
      - [-0.010, -0.005, ...] # CHITCHAT 的 1024 维权重
    bias: [0.1, -0.05, 0.0, 0.0]
```

## 五、Softmax 是什么？

### 5.1 一句话解释

**Softmax = 把任意数字变成概率分布（所有值在 0~1 之间，加起来 = 1）。**

### 5.2 例子

线性头算出的原始分数（logits）：`[2.0, 5.0, 1.0, 0.5]`

直接看：5.0 最大 → RAG 赢。但我们想知道"赢多少"：

```
softmax([2.0, 5.0, 1.0, 0.5])
= [e^2, e^5, e^1, e^0.5] / (e^2 + e^5 + e^1 + e^0.5)
= [7.4, 148.4, 2.7, 1.6] / 160.1
= [0.046, 0.927, 0.017, 0.010]
```

解读：RAG 概率 92.7%，远超其他类别 → 高置信度 RAG。

### 5.3 数值稳定性

代码中实际用的是**减去最大值**的版本，防止 e^x 溢出：

```java
// EmbeddingIntentClassifier.softmax()
double maxLogit = max(logits);  // 找到最大值
for (int i = 0; i < logits.length; i++) {
    exps[i] = Math.exp(logits[i] - maxLogit);  // 减去最大值再 exp
}
// 数学上等价，但不会溢出
```

### 5.4 一个容易踩的坑

4 类 softmax，输入 `[1, 0, 0, 0]`，最大概率是多少？

直觉：e^1 / (e^1 + e^0 + e^0 + e^0) = 2.718 / 5.718 ≈ **0.475**

不是 0.731！因为分母有 4 项（3 个 e^0 = 3 来"分票"）。

这意味着：如果 confidenceThreshold 设为 0.5，即使某个类别的 logit 比其他都高很多，softmax 后也可能不到 0.5 → 被判为"低置信度"。

**我们的处理**：测试中 confidenceThreshold 设为 0.4，种子路径断言用 `> 0.4`。

## 六、三级降级策略

### 6.1 为什么需要降级？

Embedding 调用外部 API（DashScope），网络可能超时、服务可能不可用。Agent 铁律 #1：**最外层 catch Throwable，失败降级，绝不阻断主流程。**

### 6.2 三级降级示意

```
┌─────────────────────────────────────────────────────────────┐
│                    EmbeddingIntentClassifier                 │
│                                                             │
│  Level 1: 有权重矩阵（训练完成后）                            │
│    → 线性头分类：Wx+b → softmax → 概率分布                    │
│    → 最准确、最高效                                          │
│                                                             │
│  Level 2: 无权重，有种子数据（冷启动阶段）                      │
│    → 余弦相似度分类：查询向量 vs 种子向量                      │
│    → 无需训练，但精度依赖种子质量                              │
│                                                             │
│  Level 3: Embedding 调用失败（网络/服务异常）                  │
│    → 降级到 KeywordIntentClassifier（关键词兜底）              │
│    → 精度最低，但保证主流程不中断                              │
│                                                             │
│  最外层: catch Throwable → 任何异常都走 Level 3               │
└─────────────────────────────────────────────────────────────┘
```

### 6.3 Level 2 的"种子余弦相似度"是什么？

当没有训练好的权重时，我们用"代表性查询"（种子）来代替：

```yaml
# application.yml 中的种子配置
tool-seeds:
  - query: "查看研发部门员工绩效"    # 这类查询应该走 TOOL
  - query: "团队有多少人"
rag-seeds:
  - query: "绩效制度是什么"          # 这类查询应该走 RAG
  - query: "离职流程怎么规定"
```

启动时，把种子查询也转成 Embedding 向量并缓存。

分类时：
```
用户查询: "查看员工绩效"
  → Embedding → [0.8, 0.1, 0.05, 0.02]

计算与每种种子向量的余弦相似度（夹角越小越相似）：
  vs TOOL种子"查看研发部门员工绩效" → cosine = 0.92
  vs RAG种子"绩效制度是什么"       → cosine = 0.15
  vs CHITCHAT种子"你好"            → cosine = 0.02

softmax([0.92, 0.15, 0.0, 0.02]) = [0.71, 0.12, 0.08, 0.09]
→ TOOL 概率 71% → 分类为 TOOL ✅
```

## 七、V2 vs V3 对比

### 7.1 同一个查询的不同命运

**查询："绩效怎么算"**

| 阶段 | V2 关键词投票 | V3 Embedding + 线性头 |
|------|-------------|---------------------|
| 分析 | "绩效"→TOOL+1, "怎么"→RAG+1 | Embedding → [0.7, 0.2, 0.05, 0.05] |
| 结果 | 打平，靠 chitchatScore 破平 → 可能误判 | RAG 概率 72% → RAG ✅ |
| 原因 | 关键词无法区分"问制度"和"查数据" | 语义空间天然分离 |

**查询："怎么查看员工绩效"**

| 阶段 | V2 关键词投票 | V3 Embedding + 线性头 |
|------|-------------|---------------------|
| 分析 | "怎么"→RAG+1, "查看"→TOOL+1, "绩效"→TOOL+1 → TOOL赢(2:1) | Embedding → [0.8, 0.1, 0.05, 0.05] |
| 结果 | TOOL ✅（碰巧对了） | TOOL ✅ |
| 但... | 如果改成"怎么算员工绩效"→ "怎么"→RAG+1, "算"→RAG+1(?), "绩效"→TOOL+1 → 可能误判为 RAG | 语义空间中"怎么算"和"计算规则"相近 → RAG ✅ |

### 7.2 核心差异总结

| 维度 | V2 关键词投票 | V3 Embedding + 线性头 |
|------|-------------|---------------------|
| 理解层次 | 字面匹配（哪个词出现多） | 语义理解（这句话整体什么意思） |
| 可训练性 | 不可训练（只能人工改关键词） | 可训练（标注数据 → 更新权重） |
| 冷启动 | 即刻可用 | 种子数据即刻可用，权重需训练 |
| 外部依赖 | 无 | Embedding API（有降级兜底） |
| 抗噪声 | 差（加个关键词就乱） | 强（语义空间平滑） |
| 性能开销 | < 1ms | ~100ms（Embedding 调用） |

## 八、代码在哪里？

### 8.1 核心类

| 类 | 路径 | 职责 |
|---|------|------|
| `EmbeddingService` | `infrastructure/vector/` | Embedding 服务接口 |
| `DashScopeEmbeddingService` | `infrastructure/vector/` | DashScope API 实现 |
| `EmbeddingIntentClassifier` | `core/preprocessor/router/` | V3 分类器（线性头 + 种子 + 降级） |
| `IntentClassificationPolicy` | `core/preprocessor/router/` | 配置类（权重、种子、阈值） |
| `KeywordIntentClassifier` | `core/preprocessor/router/` | V2 降级兜底 |

### 8.2 调用链路

```
QueryRouter.classify(query)
  → IntentClassifier.classify(query)        // 接口
  → EmbeddingIntentClassifier.classify()    // @Primary 实现
      → embeddingService.embed(query)       // 调 DashScope API
      → classifyByLinearHead()              // 有权重时
      → classifyBySeedSimilarity()          // 无权重有种子时
      → fallbackClassifier.classify()       // 降级时
```

### 8.3 配置入口

```yaml
# application.yml
agent:
  intent-classification:
    embedding-model: "text-embedding-v3"
    embedding-dim: 1024
    confidence-threshold: 0.5
    mixed-threshold: 0.3
    weights: []                    # 空 = 冷启动用种子
    tool-seeds: [...]              # 种子数据
    rag-seeds: [...]
```

## 九、一句话总结

**Embedding + 线性头 = 先用 AI 模型把文字变成"语义坐标"，再用加权求和判断"这个坐标离哪个类别最近"。**

它解决的核心问题：**关键词规则无法区分"语义相近但意图不同"的查询**（如"绩效怎么算" vs "查看绩效"），因为关键词只看字面，Embedding 看语义。

在我们项目中的具体作用：让意图分类从"人工编规则猜"升级为"模型从语义空间学"，同时保留三级降级保证任何情况下不阻断主流程。
